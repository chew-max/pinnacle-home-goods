# Jekyll Commerce Starter

A reusable Jekyll ecommerce storefront designed to work with the Jekyll Commerce API.

The starter provides a configurable storefront, product catalog, collections, cart, checkout, order status, policy pages, SEO metadata, responsive layouts, and GitHub Pages deployment support.

The intended workflow is:

> Clone the starter → replace store configuration, branding, content, and catalog → connect a store-specific Jekyll Commerce API deployment → validate → deploy.

A new store should not require modifications to the reusable storefront commerce engine.

## Repository Responsibilities

This repository contains the public storefront.

Store-specific presentation and configuration live here. Sensitive commerce operations such as payment processing, authoritative pricing, tax calculation, order persistence, email, and fulfillment are handled by the separate Jekyll Commerce API Worker.

## Requirements

The storefront requires:

- Ruby and Bundler
- Jekyll dependencies defined by the repository Gemfile
- A compatible Jekyll Commerce API deployment for checkout and order status
- A synchronized public commerce catalog generated by the backend repository

## Store Configuration

Store-specific frontend configuration is intentionally centralized.

### `_config.yml`

Update these values when cloning the storefront:

- `title`
- `description`
- `url`
- `baseurl`
- `logo`

For a repository-based GitHub Pages site, `baseurl` will normally contain the repository path.

For a storefront hosted at the root of a custom domain, it will normally be:

```yaml
baseurl: ""
```

The `url` value should represent the final public storefront origin.

### `_data/store.yml`

This file contains storefront-level store configuration and content.

Review and replace values such as:

- Brand name
- Tagline
- Contact information
- Checkout endpoint
- Order-status endpoint
- Navigation
- Homepage content
- Collections
- Benefits
- Policy-related presentation values

The commerce endpoints must reference the API deployment belonging to the new store. A cloned production storefront must not continue calling another store's Worker.

## Branding and Store Content

Replace store-specific assets and content as appropriate, including:

- Logo
- Product images
- Homepage imagery
- Brand copy
- About content
- Contact content
- Policy content
- Navigation and collection presentation

Store content may be changed freely without modifying the reusable commerce engine.

## Products

Product presentation pages live in:

```text
_products/
```

Each product Markdown file connects the storefront presentation to the synchronized commerce catalog through its `product_id`.

Example:

```yaml
product_id: "PRODUCT-001"
```

That value must match a product ID exported from the backend canonical catalog.

Product Markdown is responsible for presentation-oriented information such as:

- Title
- Slug
- Product ID
- Images
- Description
- Collections
- Featured state
- Badge
- SEO description
- Optional compare-at pricing

Authoritative purchasable variants and prices come from the synchronized commerce catalog rather than from product Markdown.

## Commerce Catalog

The generated public catalog is stored at:

```text
_data/commerce-catalog.json
```

Do not treat this file as the canonical product source.

The canonical catalog belongs to the backend repository at:

```text
src/catalog/products.js
```

The backend catalog synchronization process validates the canonical catalog, exports the public-safe representation, and copies it into this repository.

When the frontend repository has a different directory name or location, set `STOREFRONT_REPO_PATH` in the backend before running the catalog sync.

Example PowerShell workflow from the backend repository:

```powershell
$env:STOREFRONT_REPO_PATH="..\jekyll-commerce-starter"
npm.cmd run catalog:sync
```

A successful sync validates the backend catalog and writes the generated catalog to:

```text
_data/commerce-catalog.json
```

## Building the Storefront

Install the Ruby dependencies as required by the project, then build with:

```powershell
bundle exec jekyll build
```

The build should complete without Liquid, YAML, missing-data, or Jekyll generation errors.

Generated output is written to:

```text
_site/
```

The generated site should be inspected to verify that:

- The new store identity appears correctly
- New products are generated
- Removed starter products are absent
- Product detail routes are generated
- Collections and navigation work
- Checkout endpoints reference the intended API deployment

## GitHub Pages and Custom Domains

Before deployment, configure `_config.yml` for the intended hosting model.

Repository-based GitHub Pages deployments commonly use both:

```yaml
url: "https://ACCOUNT.github.io"
baseurl: "/REPOSITORY"
```

A root custom-domain deployment commonly uses:

```yaml
url: "https://www.example.com"
baseurl: ""
```

Also configure the repository's GitHub Pages/custom-domain settings as required by the deployment environment.

Do not leave clone-test, placeholder, or previous-store domains in production configuration.

## Clone-Safe Editing Boundary

A normal store clone may change:

```text
_config.yml
_data/store.yml
_products/
branding and images
store copy and content
policy content
generated _data/commerce-catalog.json through catalog sync
```

The following are part of the reusable storefront engine and should not normally require changes merely to create another store:

```text
assets/js/
_layouts/
cart and checkout behavior
order-status behavior
shared storefront commerce logic
```

If a new store requires engine changes solely to accommodate its identity, catalog, domain, or normal store configuration, treat that as a template portability issue rather than normal clone setup.

## Recommended Clone Validation

Before launching a cloned storefront:

1. Replace the store identity and domain configuration.
2. Replace contact and store-specific content.
3. Replace starter product Markdown and imagery.
4. Create the new canonical backend catalog.
5. Run the backend catalog validation and synchronization process.
6. Build the Jekyll storefront.
7. Confirm the generated site contains the new store and products.
8. Search source files for stale previous-store domains, product names, and branding.
9. Confirm checkout and order-status endpoints point to the new store's API.
10. Complete backend configuration and deployment validation before enabling the storefront for production commerce.
